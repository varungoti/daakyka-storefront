# DAAKYKA Storefront — Security Audit

Scope: `F:\Projects\Medical Apparel\storefront`, branch `release-hardening`, Next.js 16 App Router + Prisma 7/Postgres. Read-only audit against the running local build (`http://localhost:3000`, local Docker Postgres). No source files modified, no destructive actions taken.

## Summary

| Severity | Count |
|---|---|
| P0 Blocker | 0 |
| P1 High | 2 |
| P2 Medium | 3 |
| P3 Low | 4 |
| Info | 3 |

Overall the auth/RBAC/payment core is unusually well engineered for this stage (timing-safe comparisons throughout, server-side re-pricing, webhook idempotency, sessionVersion revocation, static RBAC-coverage tests). The two P1s are both verified live against the running server. No runtime-dependency CVEs found beyond the 14 dev-tooling advisories already noted by the team (`@lhci/cli`, `prisma` CLI chains) — those were not re-verified here since the prompt states they were already triaged as dev-only.

## Findings

| ID | Sev | Area | Title | Evidence | Impact | Fix | Effort |
|---|---|---|---|---|---|---|---|
| F1 | P1 | Abuse resistance | Rate limiting is trivially bypassed via `X-Forwarded-For` spoofing | `src/lib/security/rate-limit.ts:48-54` (`getClientIp`) blindly trusts the first hop of a client-supplied `X-Forwarded-For` header with no trusted-proxy allowlist. **Verified live**: 5 login attempts from curl with no XFF header hit 429; 8 further attempts each with a distinct spoofed `X-Forwarded-For` (`10.0.0.1`…`10.0.0.8`) all returned 401 (never rate-limited) against `POST /api/auth/login`. | Every route using `rateLimitOrResponse` (login ×2, register, forgot-password, checkout, checkout/verify, reviews, newsletter, contact, outfit try-on, admin media upload) can be hit at unlimited rate by rotating a spoofed header per request. Login is still protected by per-account lockout (10 fails/15 min, not IP-based) so credential brute force is bounded, but checkout/order-request, review spam, and newsletter/contact abuse have no other backstop. | Derive the client IP from a header only the platform itself sets (e.g. Vercel's `x-vercel-ip-*` / the last untrusted-network-boundary hop), or explicitly configure and validate a trusted-proxy chain; never trust an arbitrary client-supplied `X-Forwarded-For` value as-is. | S |
| F2 | P1 | AuthZ / IDOR | Order confirmation page leaks full PII to anyone who guesses/enumerates the order number | `src/lib/orders/get-order.ts` (`getOrderByNumber`) — no session or ownership check, documented in the code's own comment as a known trade-off. `src/app/order/[number]/page.tsx` renders full name, shipping address, phone-adjacent contact info, and line items for whatever order it finds. Order numbers are `DK-{YYYY}-{6 random digits}` generated with `Math.random()` (`src/lib/orders/number.ts`) — 1,000,000 possible values per year, not cryptographically random. **Verified**: the page is a plain Next.js Server Component, not wired through `rateLimitOrResponse` — 12 rapid sequential GETs to random `/order/DK-2026-NNNNNN` paths all returned instantly with no throttling (all 404 since no matching seeded order existed for those guesses). `noindex` is set but does not prevent direct enumeration. | An attacker can script sequential/randomized requests against `/order/DK-2026-000000`…`999999` to scrape real customers' names, addresses, and order contents at scale — a DPDP Act/PII exposure with no rate limit as a backstop (F1 also means even a future rate limit would need real IP attribution to hold). | Require either a logged-in customer who owns the order, or a signed/emailed magic-link token appended to the confirmation URL, before rendering full order details to an anonymous visitor. At minimum, add `rateLimitOrResponse` to this route and increase order-number entropy. | M |
| F3 | P2 | Payments / abuse | Unpaid "order request" fallback has no anti-abuse control beyond the (bypassable) IP rate limit | `src/lib/orders/create-order.ts:145-241` and `/api/checkout/route.ts`: when Razorpay isn't configured (confirmed live — `GET /api/health` reports `"RAZORPAY":"missing"` on this instance), every checkout creates a real `Order` in `PROCESSING` status with stock immediately decremented and **no payment step at all**. The only control is `rateLimitOrResponse(request, "checkout", 10, 60_000)`, which F1 shows is bypassable per request. Not independently re-verified by placing real orders (would have polluted the shared seeded DB), so the abuse scenario itself is **PLAUSIBLE** rather than directly reproduced, but the code path and the rate-limit bypass are both independently confirmed. | Combined with F1, an attacker can script unlimited free "orders" against real inventory, decrementing stock and generating fulfillment-queue noise/cost with zero payment. This is an intentional business fallback (COD/manual invoicing style), not a bug per se, but it currently has no CAPTCHA, no per-email/device throttle, and no manual review gate before stock is committed. | Add a stricter, IP-independent throttle (e.g. per verified email/phone, or require OTP/email confirmation before decrementing stock) for `ORDER_REQUEST` orders, and/or hold stock only provisionally until admin confirmation. Fix F1 first since it undermines any IP-based mitigation here. | M |
| F4 | P2 | Info disclosure | Unauthenticated health/status endpoints reveal internal integration and platform config | `GET /api/health` (no auth) returns which third-party integrations are configured (`SHOPIFY`, `BREVO`, `WATI`, `HERMES`, `RAZORPAY` — all "missing" on this instance) — **verified live**. `GET /api/hermes/runtime/health` (no auth) returns `{service, platform, fireworks, inline, mode}` — **verified live**, e.g. `"platform":"vercel","mode":"SUGGEST_ONLY"`. Neither leaks secrets, but both map the site's third-party attack surface / deployment fingerprint for free. | Low-severity recon aid for an attacker (e.g. confirms Razorpay isn't live so payment-bypass paths are worth targeting, confirms Vercel hosting). | Gate integration-status detail and the Hermes runtime-info payload behind `requireAdminPermission`, or strip them to a bare `{ok:true}` for public callers. | S |
| F5 | P2 | Path handling | `/cdn/[...key]` decodes path segments twice, after the traversal check | `src/app/cdn/[...key]/route.ts:14-18`: the `".."`/`"."` guard runs on the Next.js-decoded `segments`, then `segments.map(decodeURIComponent)` decodes **again** before building the R2 object key — a double-encoded segment (`%252e%252e`) passes the guard as the literal string `%2e%2e`, then decodes to `..` afterward. **Not independently exploited** (R2/S3 object keys are a flat namespace, not a filesystem path, so `..` in a key has no directory-traversal effect against `getObject`'s current implementation) — noted as a correctness/defense-in-depth gap rather than a confirmed traversal, hence P2 not P1. | If the storage backend or a future refactor (e.g. local-disk media storage) ever treats the key as a filesystem path, this double-decode reintroduces traversal. Today, worst case is `getObject` receiving an unexpected key and returning 404. | Do the traversal check *after* the final decode, and reject any decoded segment containing `..`, `/`, or `\`. | S |
| F6 | P3 | Headers | CSP allows `'unsafe-inline'` for both `script-src` and `style-src` | `next.config.ts:23-39`, explained in an inline comment as a deliberate trade-off (Next's App Router hydration scripts + inline `style=""` usage + `next/font`). HSTS is only added `if (process.env.VERCEL_ENV === "production")` (`next.config.ts:53-58`) — a non-Vercel production deploy would ship without HSTS. | Reduces CSP's effectiveness against injected inline scripts if an XSS is otherwise found; missing HSTS off-Vercel risks protocol-downgrade on first visit. | Track the nonce-based CSP migration already flagged in the code comment as a separate, larger change; make the HSTS condition `isProduction()` (already used elsewhere, e.g. `session-cookie.ts`) instead of Vercel-only. | M |
| F7 | P3 | AuthZ | `proxy.ts` admin gate checks JWT signature/expiry only, not `active`/`sessionVersion` | `src/proxy.ts:5-19` (`verifyAdminToken`) only calls `jwtVerify`, unlike `src/lib/auth/session.ts`'s `verifySessionToken`, which additionally checks `user.active` and the `sessionVersion` revocation claim against the DB. **Verified by code reading only** — not exploited, because every actual admin page/route re-checks via the full `getSession()`/`requireAdminPermission()` (confirmed in `src/app/admin/(panel)/layout.tsx:18` and in every admin API route via the static test). This is layered defense working as intended today, flagged only because the middleware's weaker check could mask a revoked session in the small window before the deeper check runs, or in a future route that forgets to call `getSession()`. | Low as-is (deeper checks always run first in every path examined) — but it's an easy place for a future route to regress into serving stale-session content. | Have `proxy.ts` perform the same `active`/`sessionVersion` check (or import `verifySessionToken` directly) so the coarse gate and the fine-grained gate can't drift. | S |
| F8 | P3 | Data validation | Admin media upload trusts the browser-supplied MIME type for the allowlist gate, but is backstopped by real image parsing | `src/app/api/admin/media/route.ts:95` checks `file.type` (attacker-controlled) against `ALLOWED_CONTENT_TYPES`, not file magic bytes. However, every accepted file is subsequently run through `sharp()` in `src/lib/media/process-image.ts:27-37`, which throws on non-image input and strips all metadata/re-encodes to WebP — so a spoofed-MIME non-image upload fails downstream rather than being stored as-is. No SVG in the allowlist, so stored-XSS-via-SVG is not reachable. | Low — the sharp re-encode is a strong practical mitigant even though the initial gate is header-based. | Optionally sniff magic bytes before the `sharp()` call to reject non-images earlier/cheaper, but not urgent. | S |
| F9 | P3 | Cron | `authorizeCron`'s dev-mode bypass is `NODE_ENV`-keyed, not environment-keyed | `src/lib/cron/authorize.ts:3-9`: if `CRON_SECRET` is unset, the function returns `true` only when `NODE_ENV === "development"` — **verified fail-closed on this instance**: `POST /api/cron/cancel-stale-orders` with no `Authorization` header and with a wrong bearer both returned 401 (this build runs with `NODE_ENV=production` despite being local). Flagged only as a naming/assumption risk: a future local setup that runs `next dev` (`NODE_ENV=development`) with `CRON_SECRET` still unset would leave every cron route open to anyone. | None today (verified closed); risk is latent for a `next dev` workflow without `CRON_SECRET` set. | Require `CRON_SECRET` unconditionally outside of an explicit test/CI flag rather than keying off `NODE_ENV=development`. | S |
| F10 | Info | Dependencies | No new runtime-dependency issues found beyond the pre-triaged dev-only advisories | `npm audit`'s 14 advisories (per the task brief) are all in `@lhci/cli` and `prisma` CLI chains — dev tooling, not shipped in the server runtime. ## What's already solid (verified, not re-litigated)

- **Admin session** (`src/lib/auth/session.ts`): HS256 JWT via `jose`, 7-day expiry, `sessionVersion` DB-checked on every read for real "log out everywhere" revocation (bumped on role/active change and admin password reset — verified in `src/app/api/admin/users/[id]/route.ts` and `.../reset-password/route.ts`). `getSession()` fails closed outside a request scope.
- **Customer session** (`src/lib/customer-auth/session.ts`): separate JWT audience (`"customer"`) from the admin token, so a customer token cannot be replayed against admin routes even with the same `AUTH_SECRET`. Same `sessionVersion` revocation pattern, bumped on password reset.
- **RBAC** (`src/lib/auth/rbac.ts`): clean permission-matrix design; every `src/app/api/admin/**/route.ts` is statically asserted (via `admin-routes-guarded.test.ts`) to call `requireAdminPermission`, and every admin page under `src/app/admin/(panel)/**` (except the shared dashboard, correctly open to all authenticated roles) independently re-checks `hasPermission` before querying data — confirmed by direct inspection of `users/page.tsx`, `customers/page.tsx`, and a full directory scan.
- **Customer IDOR guards**: `/api/account/**` protected routes are covered by `account-routes-guarded.test.ts`, including an explicit assertion that `loadOwnAddress` checks `address.customerId !== customerId`.
- **Open redirect**: `sanitizeReturnTo` (`src/lib/customer-auth/return-to.ts`) correctly rejects protocol-relative (`//`), backslash, `://`, and control-character payloads.
- **SSRF**: AR try-on (`src/app/api/outfit/try-on/route.ts`) validates both image URLs through `isTrustedImageUrl` (https-only, explicit host allowlist) before the server-side fetch — correctly designed against metadata-endpoint SSRF.
- **Payments**: server-side re-pricing (`repriceLines` in `create-order.ts` never trusts a client-supplied price), timing-safe HMAC verification for both the Checkout.js callback and the webhook (`safeEquals`), webhook idempotency keyed on Razorpay payment id, and a conditional `updateMany` stock decrement that correctly handles the sold-out-between-order-and-payment race without ever double-decrementing or failing an already-captured payment.
- **Credential store** (`src/lib/integrations/credential-store.ts`): AES-256-GCM with a fresh random 12-byte IV per encryption, auth tag verified on decrypt (tamper-evident), key length validated at 32 bytes, secrets never logged (audit log records only that a credential changed).
- **Token security**: verify-email/reset tokens are 256 bits of `randomBytes`, SHA-256 hashed at rest, single-use (`usedAt`), expiring (24h verify / 1h reset), and compared with `safeEquals` as defense-in-depth on top of the indexed hash lookup.
- **Enumeration resistance**: both admin and customer login use a precomputed dummy bcrypt hash so an unknown-email path pays the same bcrypt cost as a wrong-password path (verified by code); forgot-password always returns an identical generic response regardless of whether the email exists.
- **Lockout**: independent, per-account, DB-backed lockout (10 fails/15 min → 15 min lock) for both admin and customer logins, layered on top of (and not defeated by) the F1 rate-limit bypass.
- **Shopify webhook**: HMAC verified before any parsing, plus an explicit topic allowlist and shop-domain check — correctly rejects a signed-but-unexpected topic.
- **JSON-LD**: `escapeForScriptTag` correctly neutralizes `<`, `>`, `&` to prevent `</script>` breakout while staying valid JSON.
- **CSV import**: no formula-injection relevant surface found (numeric/enum fields are `Number()`/set-membership validated; no cell is ever written back into a spreadsheet-consumed export un-escaped — `csvEscape` quotes on comma/quote/newline). No unbounded file-size handling reviewed in the wrapper beyond this module.
- **Security headers**: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `frame-ancestors 'none'`, `object-src 'none'`, `form-action 'self'`, restrictive `Permissions-Policy` all present.
- **Cookies**: both session cookies are `httpOnly`, `sameSite: "lax"`, and forced `Secure` in production/Vercel regardless of misconfiguration (`shouldUseSecureSessionCookie` hard-codes `true` for `isProduction() || isVercel()`, ignoring a stray `COOKIE_SECURE=false`).
- **Seed-password safety**: `prisma/seed.ts`'s `isInsecureSeedPassword`/`INSECURE_SEED_PASSWORDS` mechanism blocks the documented local-dev default (and other known-weak values) from ever being used for a Vercel deploy, even if explicitly configured via `ADMIN_SEED_PASSWORD`.
